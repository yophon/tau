## 目标

清掉三条日常会碰到的技术债，不加新功能：

1. 常驻服务里一个会话换了模型后，图片支持按这个会话的模型判断（#35）；
2. 扩展的 Markdown 变换在流式输出时也生效，宽度变了按新宽度重取（#33）；
3. 把几行话经管道一次灌给 `tau --repl` 时，一句跑完再跑下一句，全部跑完才退出（#30）。

## 设计

### 1. 图片支持按会话的模型（#35）

- 工作区判断「当前模型收不收图片」时，看它的会话当前用的模型：模型表里有这个模型就看它的 `input`；不在表里（端点直连、`-m` 给的 id）照旧看进程的端点。
- 会经过这个判断的：read 工具读到图片时附不附「模型不收图片」的说明、子 agent 的工具。TUI 的 `@文件` 图片提示在客户端用 `thread/state` 的 `model` 查模型表。
- 不在常驻服务时行为不变（进程的端点就是会话的模型）。

### 2. 流式时的 Markdown 变换（#33）

- 只在会话注册了 Markdown 变换器时才做（`ThreadState.extensions.markdownTransformers > 0`），没有时一个请求也不多发。
- 流式中的文字：TUI 向中枢取它的变换结果（`isStreaming: true`），同一段文字同时最多一个请求在路上；结果回来时文字又长了就再取。重画时用最近一次的结果（比原文落后至多一个往返），这段写完时按写完的文字再取一次（`isStreaming: false`）。
- 缓存按宽度分开：终端宽度变了，屏上看得到的文字按新宽度重取，取回之前先用旧结果。
- 协议不变（`markdown/transform` 本来就带 `isStreaming` 与 `availableWidth`）。

### 3. 管道里的 REPL（#30）

- stdin 不是终端时，读到的每一行排进队列，上一句（包括它引起的工具调用与后续）跑完再取下一句；不当插话。`exit`/`quit` 在前面的都跑完后才生效。
- stdin 读完时，等队列跑完再退出；退出码照旧（最后一句失败为 1，同 `-p`）。
- 终端里的 REPL 不变：运行中输入的行照旧是插话。

## 风险

- 流式变换增加请求：只在有变换器时发、一段一个在路上，进程内中枢几乎没有代价，常驻服务是本机 socket 的往返；变换器慢时屏上的变换结果会落后得多一些。
- 管道 REPL 改成顺序执行后，原来依赖「后面的行当插话」的脚本会变（这个行为没写进文档，也不像是有意的）。
