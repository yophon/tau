# 常驻 tau：一个会话，多个客户端（总计划草案）

> 状态：已确认（2026-10-23）。用户：「都按你的建议来，去做吧」——「需要确认」五项都按建议。阶段编号 R1–R5 对应 P56–P60，每个阶段照旧先写规格书由用户判定。
> 起因：P56 规格书讨论 Codex 的 app-server 之后，用户：「这么看来我们没必要做太广，做精就行，我想要那个『一个常驻 tau，TUI、编辑器、手机同时接上同一个会话』」。

## 目标

一个常驻的 tau 进程持有会话；终端里的 TUI、编辑器、手机同时接上**同一个会话**：任何一端发的话、模型的回复、工具的进度，各端实时看到；需要审批时各端都弹，谁先答算谁的，其他端的对话框随之消失；关掉一端不影响会话，重新接上时补上错过的内容。

## 参照

| 参照 | 做法 |
|---|---|
| Codex `codex app-server`（main 分支，2026-10-23 读源码） | 协议是自定的 JSON-RPC 2.0，类型在单独的 crate，导出 TypeScript 与 JSON Schema。会话（thread）、轮（turn）、事件（item）三层：`thread/start`、`thread/resume`（**对运行中的会话就是重新接上**）、`thread/unsubscribe`、`turn/start`、`turn/steer`、`turn/interrupt`；运行中推 `item/*` 增量；审批是 server 反过来请求客户端，有人答了就发 `serverRequest/resolved` 让其他端撤掉对话框。传输 stdio、本机 socket、WebSocket（带鉴权）。**它自己的 TUI 也是客户端**：没有常驻进程时在本进程里起一个 app-server，用类型化的通道代替 JSON，语义不变；有常驻进程（`codex app-server daemon`）时自动连上共用。远程（桌面、手机经 SSH）有配对 |
| OpenCode | `@opencode/server`（HTTP，事件流，配对）+ `client` + `tui`：TUI 也是自家 server 的客户端 |
| yo-agent `surface-rpc` | WebSocket RPC、ed25519 设备配对、断线按游标续接（P53 总计划的 P57 原本要复刻的） |
| tau 现有 | `--mode rpc`（pi 的协议，一个客户端）、`--mode acp`（编辑器，一个客户端）、网关（常驻、多会话、聊天里审批，已搁置）。TUI 直接持有 Agent 对象，不经过协议（P52 复盘：要拆开得先抽一层接口） |

## 架构草图

```
               ┌──────────────── tau 服务（常驻或嵌在 TUI 进程里）────────────────┐
               │  会话中枢：每个会话一个 Agent（工作区、扩展、权限照现在的 workspace）│
               │  事件日志 + 游标：后接上的客户端从任意游标补齐                      │
               │  审批路由：请求发给所有接着的客户端，先答者为准，其余撤销            │
               └───────┬──────────────────┬──────────────────────┬──────────────┘
           进程内通道 / 本机 socket    本机 socket            WebSocket（配对后）
                    TUI               编辑器（ACP 适配）        手机（网页）
```

- **协议**照 Codex 的形状、取它的子集（会话、轮、事件、审批、问答、斜杠命令），线格式 JSON-RPC 2.0；tau 现有的 `--mode rpc`（pi 协议）与 `--mode acp` 改成这套协议的适配层，对外行为不变。
- **TUI 一律走协议**（照 Codex）：没有常驻服务时在本进程里起一个，用进程内通道；有常驻服务时连上它。这样只有一条代码路径，「多端同一会话」是自然结果。
- **常驻服务**：`tau serve`（或第一次开 TUI 时按设置自动起），监听本机 socket（Windows 用命名管道）；新开的 TUI 自动连上，`tau -r` 可以接上别的终端正在跑的会话。
- **手机**：常驻服务开 WebSocket，配对（一次性码或扫码）后，手机浏览器打开服务提供的网页客户端；不做原生 app。
- **编辑器**：ACP 适配层接到常驻服务的会话上（Zed 等支持 ACP 的编辑器直接用）。

## 分阶段（每阶段照旧先写规格书由用户判定）

| 阶段 | 内容 | 完成后能做到 |
|---|---|---|
| R1（P56） | 协议与会话中枢：协议类型（导出 JSON Schema）、进程内传输、事件日志与游标、审批路由；现有 `--mode rpc` 改成它的适配层 | 两个进程内客户端同时接一个会话，测试里验证镜像、补齐、审批先答者为准 |

## 范围外（先不做）

- 云端托管、多用户账号（只服务你自己的机器与设备）。
- 原生手机 app（先用网页）、VS Code 扩展（先用 ACP）。
- 网关（搁置中）并入：它本来就是常驻多会话，等 R3 之后再看是否改成这套服务上的一个渠道。

## 风险

- R2 是大改：TUI 现在直接调 Agent 的二十多个成员、扩展注册表的二十个、三十个选项（P52 复盘的数字）；要逐个变成协议里的方法或事件。smoke-tui 的 40 个场景是安全网。
- 扩展的界面能力（对话框、组件、状态栏）现在直接画在 TUI 里；走协议后要能远程渲染或降级（手机上组件可能只显示文字）。
- 协议一旦给手机网页用，就得稳定：先把类型和 JSON Schema 定下，后面只加不改。

## 需要确认（2026-10-23 已定）

结论：五项都按建议——1 收窄，其余复刻项搁置；2 照 Codex 的形状自定协议；3 TUI 永远走协议；4 手机用网页；5 先手动 `tau serve`，R3 加自动起的设置。


1. **收窄范围**：P53 总计划里剩下的 P56（MCP server、sampling）、P57 的 SQLite 会话库、P58 的 `createWebAgent`/`defineHttpTool`/IndexedDB/挂件、P59 不可信插件宿主，**都先搁置**（记进 Backlog），只做这条常驻多端的线（R1–R5，吸收 P57 的远程配对与 P58 的网页客户端）。建议同意：你说的「做精」。
2. **协议**：(a) 照 Codex app-server 的形状自定一套（子集），pi 的 rpc 与 ACP 做适配层；(b) 扩展 tau 现有的 pi 风格 rpc 协议到多客户端；(c) 以 ACP 为主协议。建议 (a)：Codex 已验证这套形状能撑起 TUI、编辑器、手机；pi 的 rpc 是单客户端设计（没有接上、补齐、审批撤销），ACP 是编辑器驱动单个 agent 的协议，也没有多端语义。
3. **TUI 怎么接**：(a) 照 Codex，TUI 永远走协议（没有常驻服务就嵌一个）；(b) TUI 照旧直接用 Agent，另加「把这个会话共享出去」的模式。建议 (a)：一条代码路径；(b) 两条路径会一直不一致。
4. **手机端**：(a) 常驻服务自带网页客户端，手机浏览器打开（可加到主屏幕）；(b) 原生 app。建议 (a)。
5. **常驻服务怎么起**：(a) 手动 `tau serve`，TUI 发现有就连、没有就嵌一个；(b) 第一次开 TUI 时自动起常驻服务（照 Codex 的 daemon）；可设置。建议先 (a)，R3 时加上 (b) 作为设置项。
