> 状态：已确认（2026-10-21）。用户：「都可以做，按你想法来」：每次请求的一致性检查保留、改成增量；全屏这一块的做法见 42d（与提案时说的「只渲染屏幕附近的块」不同，理由写在 42d）。
> 对应 roadmap 阶段：Phase 42
> 起因：P41 后讨论下一阶段，用户：「长会话性能有点意思」。参照：这次 Claude Code 会话的日志几天下来有 70,766 行、738 MB，几万条记录的会话是常态。

## 目标

一个几万条记录的会话，用起来和刚开始时差不多快：每轮请求、每次写入、`/resume`、全屏滚动和搜索、`/tree` 都不随会话变长明显变慢。

## 实测（2026-10-21，本机，合成的工具密集型会话）

| | 2,000 条 | 10,000 条 | 30,000 条 |
|---|---|---|---|
| 每次请求的一致性检查（整个日志 JSON 往返再比较） | 18 ms | 69 ms | 210 ms |
| 一轮 10 个工具调用的内核开销 | 84 ms | 294 ms | 831 ms |
| 每次写入的其余部分（路径、投影、用量，技术债 #17） | <1 ms | ~2.5 ms | ~8 ms |
| 冷加载一个会话文件 | 11 ms | 53 ms | 143 ms |
| `/resume` 列表，每个会话文件（整份加载） | 11 ms | 46 ms | 131 ms |
| 全屏：渲染全部行（往上滚、调整大小后） | 157 ms | 729 ms | 2.1 s |
| 全屏：第一次 Ctrl+F | 106 ms | 524 ms | 1.5 s |
| `/tree`：打开 / ↑ / 搜索框打一个字 | 5/1/4 ms | 23/5/16 ms | 68/23/59 ms |

全屏渲染的 CPU 剖析：折行（`wrap.ts`、字宽计算）和搜索语料构建占大头，GC 约一成。

## 范围内

### 42a 基准脚本

- `scripts/bench-long-session.mjs`：生成 2k、10k、30k、70k 条的合成会话（用户消息、带文字和工具调用的助手消息、几 KB 的工具结果），打印上表各项。`--sizes` 选规模。
- 它是本阶段每一步的尺子，也是以后的回归检查；不进 CI（太慢），在规格书和 development.md 里写明怎么跑。

### 42b 内核

- **每次请求的一致性检查改成增量**：保留检查本身（P22：模型看到的就是日志里的；它也能抓住下面增量投影的错）。
  - 每条记录第一次被检查时做一次 JSON 往返并缓存，以后复用；每条消息的 JSON 也只算一次。
  - 每次请求仍按日志重建一遍投影来比较（30,000 条约 3 ms），但不再序列化整个日志。
  - 代价：一条已经检查过的记录如果事后在内存里被改，不再能发现（原来能）；内核本来不改已记录的条目。
- **写入改成增量**（技术债 #17）：
  - 常见的情况是在叶子后面追加一条或几条记录，这时路径、投影、`entriesById`、用量合计都原地追加，不重建。
  - 压缩、上下文编辑、换分支（新记录不接在原叶子后面）、或存储里多出不在路径上的记录时，照旧整份重建。
  - 测试：随机的追加、压缩、编辑、换分支序列，增量结果与整份重建逐项相同。
- 目标：30,000 条时，一致性检查 ≤ 15 ms，一轮 10 个工具调用的内核开销 ≤ 100 ms。

### 42c 会话列表与恢复

- `JsonlSessionRepo.list()` 不再为每个文件建完整的条目树：逐行读出列表要的元数据（名字、最后活动时间、消息数、第一条消息）就够了（pi 的 `buildSessionInfo` 也是逐行读）。多个文件同时读，最多 10 个（pi）。
- 冷加载（`open`）找能省的：一次解析，不重复构建。
- 目标：30,000 条的文件，列表一项 ≤ 50 ms；冷加载不变慢。

### 42d TUI

- **全屏：后台预渲染**。
  - 恢复会话、调整大小、Ctrl+O 等让缓存失效之后，TUI 在空闲时分小段（每段约 10 ms）把所有块的行和搜索语料渲染进缓存，打字、重画照常进行。
  - 往上滚、选择、Ctrl+F 时如果已经渲染完，直接用；还没完就当场把剩下的做完（和现在一样）。
  - **为什么不做提案时说的「只渲染屏幕附近的块」**：控制器的滚动、拖选、复制、点击、搜索、跳到上一条提问都按整个对话的绝对行号工作，改成按块定位要重写这些交互，风险最大，真机验收也最重。后台预渲染保留这套模型，在最常见的情况下（恢复后过一会儿才往上滚或搜索）效果相同。
  - 代价：调整大小或 Ctrl+O 之后马上往上滚，仍要等剩下的部分渲染完。
- **搜索语料按块缓存**：搜索用的去样式、小写化的文字跟着块的行一起缓存，第一次 Ctrl+F 不再从头构建整份语料。
- **单个块渲染提速**：折行与字宽计算给纯 ASCII 加快速路径，减少中间数组；目标 30,000 条全部行 ≤ 1.2 s。
- **`/tree`**：过滤后的展开列表缓存起来，只在过滤、搜索、折叠、标签变化时重算；↑/↓ 只改选中位置。
- 目标（30,000 条）：预渲染完成后，往上滚到顶 ≤ 100 ms、第一次 Ctrl+F ≤ 100 ms；`/tree` 的 ↑/↓ ≤ 2 ms，搜索框打一个字 ≤ 20 ms。

## 范围外（明确不做，防蔓延）

- 缩小会话文件（工具输出照旧完整保存，Claude Code、pi 也是）；会话文件格式不变。
- `/resume` 的列表边读边显示（pi 有）：tau 的 `/resume` 只列当前项目的会话，列表变快后不需要。
- inline 模式恢复长会话时把历史写进终端：保持现状（P33 起全屏是缺省）。
- 网关（搁置中）；0.4.0 发版（推迟）。

## 风险与开放问题

- **增量投影出错**会让模型看到错的上下文：靠随机序列测试和保留的一致性检查兜底。
- **后台预渲染占 CPU**：30,000 条约一两秒，在空闲时分段做，不影响输入。
- **开放问题**：无（用户：「按你想法来」）。
