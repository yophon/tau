## 目标

不加功能，看清项目现在的样子，回答四个问题，每个结论都有数据或代码出处：

1. **它现在是什么**：和立项时的定位（D1–D12、主线计划）比，偏到了哪里；哪些部分在用、哪些是负担。
2. **它健康吗**：代码、测试、依赖、文档各有什么问题，哪些在变坏。
3. **哪些只是"做了"、没有"验证过"**：验收、真机、真端点、发布各欠着什么。
4. **接下来该做什么**：按影响排好的问题清单与后续阶段的候选（只列出，选哪个由你定）。

## 范围内

复盘分六块，每块产出「发现：证据、影响、建议、优先级（高/中/低）」：

### 52a 定位与范围

- 立项决策（D1–D12、`agent-mainline-plan`：内核为主、产品层搁置）与现状对照：P25 之后的阶段大多在 CLI 产品层，CLI 已是内核的两倍大。内核的「运行时无关」是否仍成立（纯度门禁、QuickJS、浏览器、小程序 smoke 还在跑），产品层是否反过来渗进了内核。
- 每个包的实际状态：在用 / 示例 / 搁置（网关、两个渠道包、ext-feishu、Flutter、RN、小程序示例），各自的维护成本（测试时长、每阶段要为它关掉或绕开的东西）。
- 实际用了什么（见「需要确认」2）：哪些工具、命令、模式真的被用过。

### 52b 代码健康

- 规模与增长：按包、按阶段的行数变化（git 历史），增长最快的文件，P51 门禁的上限还剩多少。
- 结构：大文件与耦合热点、跨包的重复实现、导出了但没人用的名字（脚本扫描）、`TODO`/`FIXME`/临时绕过、错误处理与日志的一致性。
- 不改代码，只记录；明显的死代码列出来，删不删留给后续阶段。

### 52c 测试与验证

- 测试：每个包的测试数与时长、最慢的测试、5 个跳过的原因、偶发记录；覆盖率用 Node 自带的 `--experimental-test-coverage` 跑一次（不装东西），列出覆盖低的模块与没有测试的模块。
- smoke 的覆盖面：38 个 TUI 场景、pack、浏览器、QuickJS 各证明了什么，没有覆盖的入口。
- 验证债：P34–P49 真机验收逐项列出（规格书里标「真机」的项）；代码就位但没实测过的路径（例如 `web_search` 真密钥、Flutter iOS、RN Android、飞书、网关真机）；真端点只测过 DeepSeek 与一个网关端点。

### 52d 依赖、发布与外部对照

- 依赖：各包依赖的版本与上游最新版的差距（`npm outdated`，只读）、`npm audit`（只读）、钉死版本的依赖（pi-codemode、ink、undici、highlight.js）是否该跟。
- 发布：0.2.0 之后累积的破坏性变更清单（从 CHANGELOG 整理），一直不发的代价；技术债 #13（四个包从没发过）。
- 外部参照：pi 上游现在的 tag 与 tau 钉的 v1.4.0 差多少，Claude Code 最新版与 tau 照抄时的版本差多少。只记差距，不规划功能。

### 52e 文档与流程

- 文档：用 P50/P51 的脚本再扫一遍名字；CHANGELOG 的组织（1400 多行的 `[Unreleased]`）。
- 流程：每个阶段从规格到 CI 绿的提交数、验收时才发现的问题（各规格书「实施记录」里的「验收中发现」）、规格偏差的次数、CI 失败的历史（`gh run list`）、反复出现的坑（构建工具、Windows、WSL、smoke）。九天 32 个阶段的节奏对质量的影响，用这些数据说话。
- 技术债表逐条重评：还成立吗、优先级对吗、有没有该登记而没登记的。

### 52f 对照 yo-agent 的 TUI（用户加的）

tau 的 TUI 在 P25 照 yo-agent 的 surface-cli 重写，之后两边各自发展。后续可能把 tau 的 TUI 摘出来替换 yo-agent 的，这一块为那个决定准备材料：

- **功能对照**：读 yo-agent 现在的 TUI 代码与文档，逐项列出 yo-agent 有、tau 没有的功能（交互、命令、显示、按键、与 yo-agent 运行时的接口），反过来 tau 有、yo-agent 没有的只列个数与大类。每项注明在 yo-agent 里的位置、是否依赖 yo-agent 特有的运行时能力。
- **摘出来的可行性**：tau 的 `packages/cli/src/tui/` 依赖了什么——内核的类型与 `Agent` 方法、CLI 根目录的模块（会话标题、handoff、git、状态栏、push 通知等）、宿主能力。哪些是界面本身、哪些是 tau 的产品逻辑；要摘成可复用的包，接缝应该划在哪、要断开多少处依赖。只评估，不动手。
- 结论写进复盘文档的单独一节，并列为后续阶段候选之一。
