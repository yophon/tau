# Phase 47：MCP 2026-07-28 新规范（照 Claude Code 与官方 SDK 2.x）规格书

> 状态：已完成（2026-10-22）。「需要确认」七条用户都按建议定（「按你的建议来，去做吧」）。实现与偏差见文末「实施记录」。
> 对应 roadmap 阶段：Phase 47
> 起因：P44 时定为单独立项（D47），P44 之后用户同意纳入计划；P46 完成后用户：「开搞吧」。

## 目标

1. **两代协议都能用，用户不用配置**：tau 连 MCP 服务器时先问它支不支持 2026-07-28。支持就用新协议，不支持就照旧握手（2025-11-25 及更早）。这是 Claude Code 的做法。
2. **新协议下现有功能照常工作**：
   - 工具、资源、提示命令、`@` 引用；
   - elicitation 的表单和网页两种方式；
   - 进度、取消；
   - 工具和提示列表变化后自动刷新。
3. **补上新协议要求客户端做的事**：
   - 每个请求自带版本和能力；
   - HTTP 的标准请求头；
   - 多轮请求：服务器要补充信息时不再反过来发请求，而是返回「需要输入」，tau 问完用户后带着答案重发；
   - 用 `subscriptions/listen` 收变化通知；
   - 工具参数上标了 `x-mcp-header` 的，把参数值镜像成请求头。
4. **OAuth 补上新规范的最后一项**：客户端凭据按签发它的授权服务器存，授权服务器变了就重新注册。

## 参照（2026-10-22 查阅）

pi 没有跟进这一版。pi 1.2.0 的一致性测试里明确写着：2026-07-28 是一种 pi 不支持的无状态协议。上游的 pi 1.3.0 和 1.4.0 的 MCP 包也没有变化。所以这一阶段参照规范原文、官方 TypeScript SDK 2.x 和 Claude Code。Claude Code 的 v2 运行时就建在官方 SDK 2.x 上。

## 范围内

### 47a 协商与传输（ext-mcp-http 客户端、ext-mcp）

- **两代协议**：
  - 新协议只有 `2026-07-28`；
  - 旧协议照旧，包括 2025-11-25、2025-06-18、2025-03-26、2024-11-05。
- **连接时怎么定**（`protocolNegotiation` 选项）：
  - **`"legacy"`**：照旧握手，不探测，和现在一模一样。纯 ES 包（浏览器、小程序、RN 宿主）缺省用这一档，同官方 SDK。
  - **`"auto"`**：先发 `server/discover`，请求的 `_meta` 按新协议填：
    - **回 DiscoverResult**：用新协议。服务器的能力和 instructions 从这里取，服务器名字从结果的 `_meta` 取。
    - **回 `-32022`**：是新协议服务器，但不支持 2026-07-28。它列出的版本里有 tau 认识的旧版本，就用旧协议握手；没有就报错，并写明它要的版本。
    - **stdio 上**：其他回复都算旧服务器，照旧握手，包括别的错误、超时、进程在探测时退出。退出的情况先重启一次再握手。
    - **HTTP 上**：
      - 回的是新协议的错误（`-32020`、`-32021`、`-32022`），按新协议服务器处理；
      - 别的回复算旧服务器，照旧握手。包括空正文、旧服务器的「未初始化」错误、`-32601`。
      - 401/403：先走现有的授权流程，再重新探测。它们不算新旧证据。
      - 5xx 和超时：算连不上，走现有的重试与报告，不当成旧服务器。
  - **探测超时**：用这个服务器的握手超时，即 mcp.json 里的 `timeout`，缺省 10 秒。官方 SDK 也是沿用请求超时。
  - **结果记在服务器上**：这次运行里重连不再探测（见「需要确认」3）。连不上时，或新协议请求被拒绝时，清掉记录，下次重新探测。规范要求判断失效时重新探测。
- **新协议下的请求**：
  - 每个请求的 `params._meta` 带三项：`io.modelcontextprotocol/protocolVersion`、`clientInfo`、`clientCapabilities`。
    - 宿主能问用户时，能力里声明 `elicitation: {form: {}, url: {}}`；
    - 配置了 roots 时，声明 `roots: {}`。
  - 不发 `initialize`、`notifications/initialized`、`ping`（tau 本来也不发 ping）。
  - 服务器反过来发的请求一律回「方法不存在」。新协议的服务器本来就不该发。
  - 检查结果的 `resultType`：
    - 没有这个字段或值为 `"complete"`：照常处理；
    - `"input_required"`：进入多轮请求（见 47b）；
    - 其他值：当无效结果报错。
  - 错误码 `-32021`（缺客户端能力）在报错里写出缺哪几项。
  - 请求中途收到 `-32022`，说明服务器换了版本：断开，下次连接重新探测。
- **Streamable HTTP 走新协议时**：
  - **请求头**：每个 POST 带 `MCP-Protocol-Version` 和 `Mcp-Method`；tools/call、resources/read、prompts/get 再带 `Mcp-Name`。值不是纯可见 ASCII，或者碰巧长得像编码标记时，用 `=?base64?…?=` 编码。
  - **去掉的东西**：没有会话 id，没有 GET 流，没有 `Last-Event-ID` 续传，关闭时也不发 DELETE。
  - **取消**：中止 fetch，关掉这个请求的响应流，不发 `notifications/cancelled`。
  - **断流**：响应流在回复到达前断了，用新的 id 重发一次（规范要求，见「需要确认」5）。再断就报错。
  - **400 带 JSON-RPC 错误正文**：把这个错误原样交给调用方，不再笼统报「HTTP 400」。
- **stdio 走新协议时**：消息格式不变；取消照旧发 `notifications/cancelled`；订阅的通知按 `subscriptionId` 分到对应的订阅。

### 47b 新协议下的功能（ext-mcp-http）

- **多轮请求（MRTR）**：tools/call、prompts/get、resources/read 返回 `input_required` 时：
  - **`elicitation/create`**：交给现有的 elicitation 处理，也就是 P44 的对话框，`Elicitation` 钩子照样生效。
    - 网页方式：用户同意打开网页后立刻重发，浏览器那边做完没有由服务器判断。
    - 服务器再次要求时就再问一次。规范要求客户端让用户能重试或取消。
  - **`roots/list`**：用配置的 roots 直接回答，不弹框（Inspector 也是这样）。
  - **`sampling/createMessage`**：tau 不声明 sampling，服务器本不该要。真要了，这次调用就报错，说明不支持。
  - **重发**：
    - 用新的 JSON-RPC id；
    - 原请求的参数加上 `inputResponses`，键用服务器给的；
    - `requestState` 原样带回，服务器没给就不带。
  - **上限**：最多 10 轮（官方 SDK 的缺省），超过就报错。
  - **中途取消**：用户按 Esc 或调用被中止，就停下，不再重发。
- **变化通知（`subscriptions/listen`）**：
  - 连上新协议服务器后，按它声明的能力开一条订阅：
    - `tools.listChanged` 对应 `toolsListChanged`；
    - `prompts.listChanged` 对应 `promptsListChanged`；
    - `resources.listChanged` 对应 `resourcesListChanged`；
    - 一项都没有就不开。
  - 收到 list_changed 后走现有的刷新：重新注册工具、重列提示命令、作废资源补全的缓存。
  - 断开时（服务器没发正常结束的回复）就重开（照 Claude Code）。退避同现在的 GET 流：从 1 秒起翻倍，最多 30 秒；连续失败 5 次就停下并报告。
  - 服务器正常结束了订阅，或一直没发确认，就不重开（同 Inspector）。
  - HTTP 上这条流和旧协议的 GET 流共用一个开关：纯 ES 包的 `serverNotifications` 缺省关（移动端不保持空闲连接），CLI 打开。stdio 上一直开。
- **`x-mcp-header`**（只在 HTTP 走新协议时）：
  - **列工具时校验**：按规范的约束检查工具参数上的 `x-mcp-header`。不合法的工具不注册，报告工具名和原因，其他工具不受影响（规范要求）。
  - **调用时镜像成请求头**：被标注参数的值放进 `Mcp-Param-{名字}`。字符串原样，整数用十进制，布尔用 `true`/`false`，不安全的值用 base64 编码。参数没给或为 null 时不带这个头。
  - **回 `-32020`**（请求头和正文不符）：重新列一次工具，再重发一次。
- **新协议里不做的可选部分**：
  - 缓存提示只解析，不缓存（见「需要确认」4）；
  - 日志：不带 `logLevel`，服务器就不发日志，和现在一样；
  - Tasks 扩展：tau 不声明它，服务器就不会返回任务。

### 47c OAuth（ext-mcp）

- **凭据按授权服务器存（SEP-2352）**：
  - 保存客户端注册信息时，记下签发它的授权服务器（issuer）。
  - 发现授权服务器变了（服务器的资源元数据指向另一个授权服务器），就不再用旧的注册信息和令牌，重新注册、重新登录。
- 新规范的其余 OAuth 要求 tau 已经有了：
  - RFC 9207 的 `iss` 校验（P32b，照 pi 1.0）；
  - `application_type`（照 pi 1.0.4）；
  - CIMD（照 pi 1.0.1）；
  - token 端点必须是 HTTPS，本机回环地址除外。

### 47d CLI 与文档

- **CLI 缺省 `auto`**，HTTP 和 stdio 都探测（照 Claude Code）。
  - `TAU_MCP_PROTOCOL_NEGOTIATION=legacy` 关掉探测，`auto` 打开；其他值忽略并给出警告。
  - 对应 Claude Code 的 `MCP_PROTOCOL_NEGOTIATION`，加了 `TAU_` 前缀。
- **显示协议版本**：`/mcp` 和 `tau mcp list` 在每个服务器后面写上协议版本，`2026-07-28` 或握手协商出的旧版本。`tau mcp list` 的连接检查也走同样的协商。
- **网关**（搁置中）：保持 `legacy`，行为不变。
- **文档**：
  - D50；
  - connectors.md 的 MCP 一节：两代协议、怎么探测、怎么关掉探测；
  - architecture、README、CHANGELOG、roadmap。
  - pi-parity 不涉及，pi 没有这些。

## 需要确认（2026-10-22 已按建议确认）

1. **CLI 缺省探测，照 Claude Code**：
   - 官方 SDK 提醒过：每次运行都新起进程的 CLI 不要缺省用 `auto`。原因是完全不回应的旧 stdio 服务器会让连接多等一个探测超时。
   - Claude Code 还是缺省探测 stdio。
   - 建议照 Claude Code：CLI 缺省 `auto`，`TAU_MCP_PROTOCOL_NEGOTIATION=legacy` 关掉；纯 ES 包缺省 `legacy`，同官方 SDK。
2. **stdio 在哪个进程上探测**：
   - 官方 SDK 每次都另起一个一次性的进程专门探测，因为有的服务器收到握手前的请求就退出。这样每个 stdio 服务器每次连接都要启动两遍，用 npx、uvx 起的服务器启动一次就要好几秒。
   - 建议直接在真正的服务器进程上探测：
     - 它回错误，就在同一个进程上接着握手；
     - 它在探测时退出，就重启一次再握手；
     - 探测之后握手失败，也重启一次再试。
3. **探测结果只记在这次运行里**：
   - 重连不再探测，也不写盘。
   - 代价：每次启动 tau（包括每次 `tau -p`）都要探测一次。
     - 对正常回错误的旧服务器，只多一个来回；
     - 对完全不回应的旧服务器，要多等一个握手超时（缺省 10 秒）。连接在后台进行，不挡输入，只是这个服务器的工具晚到；也可以用环境变量关掉探测。
   - 写盘能省掉这些，但服务器升级以后，旧的判断会让 tau 悄悄继续走旧协议，还得另做过期。建议先不写盘。
4. **缓存提示只解析，不做响应缓存**：
   - Claude Code 和官方 SDK 都不会因为缓存过期就主动重新拉列表。tau 的工具列表本来就在整个连接期间留着，靠变化通知刷新。
   - SDK 还有一层响应缓存：重复读同一个资源时，直接返回还没过期的结果。规范里这是可选的，建议 tau 不做。
5. **断流重发**：
   - 规范要求：响应流在回复到达前断了，就用新 id 重发。
   - 风险：tools/call 被重发时，服务器可能已经执行了一部分。
   - 建议照规范重发一次，只在网络断开时重发；超时和用户取消不重发。
6. **新协议下继续提供 roots**：
   - 规范把 roots 标为弃用，但弃用期内完整可用。tau 现在把工作目录作为 roots 提供（P43）。
   - 建议继续提供：新协议的服务器经多轮请求要 `roots/list` 时，照样回答。

### 偏差

- **接口草案里的 `setProtocolEra` 没做**：HTTP 传输按每条消息判断，请求的 `_meta` 里带新协议版本就按新协议发（加请求头、把 4xx 的 JSON-RPC 错误交回、断流交给调用方重发），同官方 SDK 的做法。传输加了 `kind`（`http`/`stdio`），客户端据此决定取消方式和探测超时的含义。
- **`-32022` 列出的版本里有 2026-07-28 时重试一次**：探测和新协议请求都是。规格只写了「列出旧版本就握手」；一致性测试的 `request-metadata` 场景先模拟拒绝一次，tau 原来直接报错。
- **授权流程带着 401 的 challenge 进入时、以及每次交互登录时都重新发现授权服务器**：47c 原来只在发现结果变了时作废旧注册，但 tau 一直沿用缓存的发现结果，看不到变化。一致性测试的 `auth/authorization-server-migration` 场景暴露了这一点。官方 SDK 也要客户端自己在重新授权前重取资源元数据。
- **ACP 模式也缺省探测**：规格写的是 CLI，ACP 也是 CLI 宿主，一并做了。
- **接口多出来的**：`McpClient.excludedTools`、`McpSubscriptionError`（`listen()` 在确认之前结束）、`createMcpServers` 的 `listChanged(config)`；导出 `MCP_ERROR_CODES`、`MCP_META`、`headers.ts` 的几个函数。

### 验收中发现并修掉

- 探测：`-32022` 带着 tau 自己的版本时没有重试（见偏差）。
- SEP-2352：沿用缓存的发现结果，看不到授权服务器变了（见偏差）。
- **P24 起就有**：读 SSE 回复时 `reader.cancel()` 的 Promise 没人处理，紧接着请求被中止，它以 `"settled"` 被拒绝，`tau -p` 因未处理的拒绝退出。用 SSE 回复的 HTTP 服务器（比如 2025 版官方 SDK 的无状态服务器）都会触发。官方服务器加真 DeepSeek 验收时发现。
- **P24 起就有**：第一次提示等「带直接工具的服务器」最多 10 秒的计时器，服务器先连上以后没有取消，有 MCP 服务器时 `tau -p` 做完还要等到 10 秒才退出。写 CLI 测试时发现。
- 测试里修正：脚本化服务器转调时丢了 JSON-RPC id（订阅测试挂住的原因）。

### 真 DeepSeek（deepseek-flash）加官方服务器

四个服务器：官方 SDK 2.3.1 的只认新协议的服务器（HTTP 用 `createMcpHandler`，stdio 用 `serveStdio`，都是 `legacy: "reject"`），和仓库里官方 SDK 1.29 的只认旧握手的服务器（HTTP 无状态、stdio）。装在 scratchpad 临时目录，验收后删除。

- `tau mcp list --check`：两个新协议服务器显示 `MCP 2026-07-28`，两个旧的显示 `MCP 2025-11-25`。

### 官方一致性测试（`@modelcontextprotocol/conformance@0.2.0-alpha.12 client --requirements 2026-07-28`）

被测客户端是 tau 自己的客户端（`protocolNegotiation: "auto"`、elicitation 一律接受、tau 的 OAuth 登录加模拟浏览器）。要计分的 32 个客户端场景：

- 30 个通过：`tools_call`、`request-metadata`（7/7）、`sep-2322-client-request-state`、`http-standard-headers`、`http-custom-headers`（18/18）、`http-invalid-tool-headers`、`json-schema-ref-no-deref`，以及授权场景里的元数据发现、作用域、三种 token 端点认证、预注册、资源不符、离线访问、授权服务器迁移（27/27）、`iss` 校验六项。
- 2 个失败：`auth/metadata-var3`、`auth/scope-step-up`。另有 3 条警告：`auth/basic-cimd`（tau 没有公开的 CIMD 文档）、`auth/scope-from-www-authenticate`、`auth/scope-step-up`。原因是 P32b 移植 OAuth 时与 pi 1.2 的两处差距：交互登录不带 401 的 challenge（资源元数据地址与作用域）；403 `insufficient_scope` 不触发升级授权。pi 1.2 在 2025-11-25 下这两个场景都通过。这与 2026-07-28 无关，登记为技术债 #23。
- 不计分的扩展场景（客户端凭据、DPoP、企业授权、WIF）和发布后新加的 `json-schema-2020-12-preservation` 未通过：tau 没有实现这些扩展。
